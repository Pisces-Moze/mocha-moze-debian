## 已测结果及边界

- 5 V / 2 A 供电、852 MHz、无后台高频 fork 采样时，600 帧窗口测试（另有 120 帧预热）：60.042 FPS，P95 17.014 ms，P99 17.469 ms，超过 25 ms 为 0。低开销单 Python 采样时 59.744 FPS，P99 20.775 ms、4 帧超过 25 ms。不是任意应用、视频或完整桌面的长期 60 FPS 保证。
- 之前每秒大量 `cat` 子进程的监测会明显干扰测量，不能用该组 FPS 与无采样测试直接比较。使用单进程低开销采样，并同供电、同频率比较。
- GPU DMA-BUF → Tegra atomic KMS 的输出 fence 测试：CPU 预等待对照和异步 IN_FENCE_FD 两组各 120 帧、各 120 次导出时未完成的 fence，约 30.02/30.03 FPS；测试代码没有 glReadPixels、CPU map 或像素复制。测试本身的帧率不能当作合成器帧率。
- 完整 Niri 旧 Smithay 的 395 帧对照全部 `needs_sync=true`，平均等待 1.610 ms；仅换 native-sync Mesa 的 381 帧仍全部 true，平均等待 0.938 ms。这直接证明“Mesa 导出 fence 成功”不等于完整合成器已消除 CPU wait。
- 稳定桌面仍有偶发卡顿。新 Smithay 修复的实际 `supports_fencing=true`、`needs_sync=false` 和 wait_ms=0 尚未验证。
- 电脑 500 mA USB 下高负载曾测到 3.534 V、净放电约 1.496 A；墙充改善供电。先前黑屏/断连根因未确认，不能只归因于电量、sync 或超频。GPU 75°C→648 MHz、冷却后→852 MHz 的用户空间热策略已实际触发。

## 正在构建的同步候选

Smithay 用 DRM driver description 中的 `NVIDIA` 判定旧闭源驱动。Tegra 的 name 是 `tegra`、description 是 `NVIDIA Tegra graphics`，因此被误判并禁用 explicit fencing。0009 按 `nvidia`/`nvidia-drm`/`nvidia_drm` 驱动名判定，保留真实旧闭源 NVIDIA 的版本排除，不直接删除同步等待。

0008 在 GK20A 且 `MOCHA_NATIVE_FENCE=1` 下启用 sync_file：每个输出 fence 使用独立 4 KiB GART BO，提交后从 dma_resv 导出，避免等待 CPU 或导出被后续无关任务复用的 query BO。导入 FD 会复制并正确关闭；导入依赖的 server_sync 仍保守地等待 CPU，**不是所有方向都已实现 GPU server wait**。

构建虚拟机曾重启，留下截断的 Smithay rlib；已清理该依赖，并验证其余 238 个 rlib 完整后重建。源码和脚本保留在构建机，不能使用重启前 `/tmp/niri-native-fencing` 的旧产物冒充修复版。新的二进制在完整构建、marker 检查及 SHA256 通过前都算待完成。

## 远端 Codex 第一轮

1. 读本文件、`docs/TODO.md`、desktop 的 `docs/NATIVE-PERFORMANCE.md` 和两个 lock JSON，确认工作区/设备状态；不要重刷已安装 Debian。
2. 在平板只读检查 `uname -r`、`cat /proc/cmdline`、`cat /sys/devices/system/cpu/online`、`findmnt /`、`systemctl --failed`、`dmesg`、电量/电压/充电输入限额。默认系统与临时 native 系统必须分清。
3. 用本机已有验证过的 U-Boot 临时选中 native 内核。若在充电界面，按住电源约 2 秒进入桌面；若 software reboot 已失联，只能按键进原厂 Fastboot。不要使用 `reboot bootloader`，实测会进 APX。
4. 保留现有可用库与默认引导，把新 Mesa/Niri 放独立目录；先停止所有固定频率策略，再受控设置本机 852 MHz，并确认接 5 V / 2 A 充电器。不要热卸载 Nouveau。
5. 按 desktop 文档跑独立 sync_file / KMS 对照，再用 `performance/profile-installed-prototype.sh` 对完整 Niri 记录 renderer、实际 maps、`supports_fencing`、`needs_sync`、wait_ms、P95/P99 和电源/温度。原型机脚本依赖 UID 1000、mocha 用户及当前目录，不可直接当作通用安装器。
6. 候选不稳定就删运行时 service override、重启原 Niri、恢复 auto 或已验证策略；不要写默认引导。失联后由 RAM 系统先检查未挂载文件系统，再恢复。FS 修复时不能对正在挂载的根分区执行 e2fsck。
7. 把真实结果、失败与剩余任务回写同一草稿 PR。仅测得 needs_sync=false 不足以验收：需要完整画面、触控、亮度、视频/浏览器负载、墙充/电池、DPMS 和普通冷启动。

## 临时从 eMMC 引导（不会 flash）

已有原型机 APP 中的上述文件时，`tools/boot-installed-native.py` 提供可移植参数化版本；第一次装 Debian 应走 [INSTALL.md](INSTALL.md)，不能用此脚本替代分区安装步骤。

```sh
python3 tools/boot-installed-native.py --help
python3 tools/boot-installed-native.py --fastboot fastboot --factory-serial YOUR_FACTORY_SERIAL \
  --uboot-serial YOUR_RAM_UBOOT_SERIAL --loader /path/to/verified-ram-uboot.img \
  --loader-sha256 YOUR_VERIFIED_SHA256 --diagnostic
```

此脚本只发 `boot` 和 `oem run`，从 APP 读三个文件，不写 LNX/APP。`--diagnostic` 暂停自动桌面和固定 GPU 策略。不要沿用维护者设备的序列号、PARTUUID 或网络地址。

本次公开源码检查：所有 Mesa/Smithay/Niri/Noctalia 补丁在固定上游源码应用成功；8 组 fence、4 组 reset/scissor、modifier 6 次往返与 4084 种其他布局回归通过，三个 ARMhf 探针交叉编译通过。九个 Mesa 补丁文件与实际构建工作树逐字节相同。见 [构建检查输出](diagnostics/2026-10-11-public-source-validation.txt)。这些结果不替代新 Niri 的实机验收。
