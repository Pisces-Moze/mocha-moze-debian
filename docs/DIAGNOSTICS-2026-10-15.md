# 2026-10-15 DFLL 步长修复与有限桌面验收

Palmas 电压表步长候选已经过两次 RAM 冷启动：LUT 恢复有效选择器，固定请求 204/408/612/1020 MHz 的独立 PMU 对照、受限 schedutil 桌面、32 MiB 和 128 MiB 混合数据 LZ4 压缩回读与有限图形缓冲检查通过。用户两次确认画面、触控、概览底部图标与顶部弹窗，第一次启动还确认电源熄屏／唤醒／密码解锁正常。默认引导未改变；完整电压曲线、CPU idle 与长期多应用压力仍待验证。下面保留原始失败和修复后的证据。

## 原始 DFLL 开启重测：失败

同一 `6.12.111-moze.1-native-runtime` 内核重新使用开启 DFLL 的设备树，修正诊断服务的数据分区依赖，并在挂载后加载匹配的无线／背光模块。USB SSH、Wi-Fi SSH 与 framebuffer 均恢复，CPUFreq policy0 建立。首次未连接不能作为 DFLL 启动失败的证据；其中存在早期模块路径不可用的干扰。

但调频验收失败：powersave 请求 204,000 kHz，软件上限设为 612,000 kHz，CCF 同样显示 204 MHz；DFLL 闭环状态为 1，硬件监测却为约 1.85–1.9 GHz。只对诊断进程自身计数、绑定 CPU0 的 ARM Cortex-A15 PMU 周期测量也得到约 1.855 GHz，与软件请求明显不符。

| 读数 | 值 |
| --- | --- |
| CPUFreq 请求 | 204,000 kHz |
| DFLL 内部监测 | 1,874,250,000 Hz |
| 诊断进程用户态 CPU 周期 | 926,696,244 |
| 同段线程 CPU 时间 | 499,517,499 ns |
| PMU 估算实际频率 | 约 1,855,182,743 Hz |

PMU 只计用户态周期，时间包含少量系统开销，所以该估算不是精密校准；它足以独立否定“CPU 正在 204 MHz 运行”的结论。DFLL monitor 的上游实现按参考时钟、输出 scaler 计算实测频率，不能用 `scaling_cur_freq` 的请求缓存代替它。

本轮在启动桌面、GPU 负载和提高 CPU 上限前停止。没有手动写电压、修改 CVB 表或将候选提升为默认；默认仍是已验收的 native 内核。后续需要定位闭环、输出 scaler、PMIC I2C/LUT 与实际控制的对应关系，不能仅凭 governor 写入成功或 OPP 列表宣称调频正常。

运行时策略新增启动前硬件频率检查：稳定请求与 DFLL monitor 明显不符时，在任何 governor／上限／swap 修改前拒绝启动。原六项策略回归包含本轮 204 MHz 请求／1.874 GHz 实测的不匹配案例，随后补充过渡采样两项，总计八项通过。此防护不修复 DFLL 硬件控制，也不意味着已完成降压或长期性能调教。

原型机随后按正常引导恢复 `6.12.111-moze.1-native`，用户确认桌面恢复；SSH 核对 Niri/Nyxuri 进程、背光 171/255 和两进程实际加载的最终 Mesa 路径。临时诊断服务已移除，默认内核与 DTB 哈希保持原值。

## Palmas 分段电压表步长修复

源码检查发现 Palmas SMPS 使用分段电压表，`regulator_get_linear_step()` 读取的 `uV_step` 为零；DFLL 却用它除电压索引。新的内核候选从受板级约束的有效电压项推导均匀正步长，跳过零项与重复平台，拒绝非均匀／倒序／单电压表，保持原厂 CVB 与电压范围；实际驱动函数的十项 C 回归通过。

候选已完成 Image、模块、DTB、uImage 与匹配背光模块构建，release 为 `6.12.111-moze.1-native-runtime`；构建机与提交的 DFLL 源文件 SHA256 一致。构建通过不能替代调频实机验收。

## 第一次 RAM 启动：固定档位和桌面

候选 LUT 不再全零，有效选择器为 `0x2e..0x44`，DFLL 输出配置为 `0x41160000`。保持 `cpuidle.off=1`，先在 powersave 下验证请求 204 MHz、monitor 约 219–221 MHz、PMU 约 218 MHz，CPU 电压读回 900 mV，然后使用 2 A 墙充做有限固定档位对照。PMU 只计诊断进程自身用户态周期，每次约 0.2 秒，不进行全局 PMU 采样或手动电压写入。

| 请求 MHz | DFLL monitor MHz | 独立 PMU MHz | CPU 电压 mV |
| --- | --- | --- | --- |
| 204 | 221.133 | 218.383 | 900 |
| 408 | 436.289 | 431.054 | 900 |
| 612 | 651.943 | 649.612 | 900 |
| 1020 | 1084.597 | 1081.846 | 900 |
| 612 | 651.943 | 650.936 | 900 |
| 204 | 224.818 | 217.326 | 900 |

实测随请求变化，但比请求高约 6%–8%；这些点处于 900 mV 平台，不能称为精密频率校准或完整电压调节验收。没有测试高于 1020 MHz 的请求。

schedutil 切换初段出现过渡 monitor 样本，原策略因此拒绝首次桌面激活并恢复原 governor／上限，没有继续启动 GPU。保守 612 MHz 上限下独立 PMU 三次约 646–652 MHz。策略保留原匹配误差阈值，在最多 20 轮有界窗口要求同一请求连续两次匹配，拒绝持续错误与偶然单次匹配。修正后只在当前启动启用 schedutil、1020 MHz 请求上限与匹配 Nouveau，不安装或启用候选策略的永久服务。

完整 Niri/Nyxuri 实际加载最终 Mesa；用户确认画面、触控、概览图标与顶部弹窗正常，随后确认短按熄屏保持约 20 秒、再次短按唤醒及触屏密码解锁正常。20 轮概览、20 轮控制中心开关及随后空闲均保持 8 个 DMA-BUF、40,685,568 字节；可用内存约 1.22 GiB，没有本轮图形缓冲累积。

384 MiB 逻辑容量 LZ4 zram 上，32 MiB 自有匿名页 pageout／SHA256 回读一致，压缩期间 zram 物理用量约 532 KiB，释放后约 40 KiB。MGLRU/PSI 可读；这是有限功能检查，不是长期全系统压力测试。

## 第二次 RAM 冷启动与混合数据回读

使用同一 uImage／DTB 再次冷启动，低频预检通过；204 MHz 请求对应 monitor 221.133 MHz、独立 PMU 217.693 MHz，电压读回 900 mV。受限 schedutil、1020 MHz 请求上限和完整 Nyxuri 再次启动，用户确认画面、触控、概览图标和顶部弹窗正常。Niri／Noctalia 可执行文件和实际映射的最终 Gallium SHA256 均再次核对。

第二轮 32 MiB 回读通过。另做 128 MiB 自有匿名页测试，交替放入可压缩页与随机不可压缩页；pageout 后物理 zram 占用 68,173,824 字节，全部数据 SHA256 回读一致，释放后降至 151,552 字节。过程中没有启动全系统内存压力工具；回读造成短暂 PSI 等待，随后 `avg10` 回落到零。这不等同于长期多应用低内存验收。

修正策略服务首次初始化时短暂超过用户／熄屏／温度上限的问题：在启用 schedutil 前先应用当前限制，而不是等第一轮主循环。新增实际主循环的四种启动条件子案例，总计九项策略回归在 Windows 与 ARM 原型机通过。用隔离的 1020 MHz 偏好临时运行真实策略 40 秒，保留已有 zram，退出恢复原 CPU governor／上限和 swappiness；永久策略服务未安装或启用。测试结束 CPU／GPU 约 63／59°C，无失败 systemd 服务。

默认 uImage 与 DTB 哈希保持此前已验收值。候选的默认提升未验收，CPU idle 保持关闭；完整电压曲线／频率校准、长期热稳定、多应用内存压力及其他硬件任务继续保留。筛选后的有限数值证据见 [JSON 记录](diagnostics/2026-10-15-dfll-alignment.json)。
