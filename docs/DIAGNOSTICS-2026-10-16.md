## 充电界面与电源启动

充电 UI 使用 90° framebuffer 变换，对应桌面的 270° 输出变换。原先一次性生成整套动画帧会长时间阻塞线缆状态轮询；现改为每轮至多生成一帧，优化像素打包和采样表，已准备帧可立即显示。真实变换函数与旧像素结果对照覆盖四方向及 18 种格式／透明度／缩放组合。

最终 UI SHA256 为 `9d321e3f516e2b8882c90496124d3a8e6210cf225dd26f2d46233ae577038990`，已持久安装。用户确认充电方向、自动熄屏后拔线约 2–3 秒再插回唤醒、充电界面长按电源进入桌面正常。本轮 UI 内首屏约 0.68 秒；该值不包含引导器、内核和数据分区挂载时间，不能当作整机冷启动到充电画面的耗时。

先前仅在 U-Boot bootcmd 中读取 Q0，显示初始化后可能已错过启动按键。新增 board early hook，先将 Q0 配成与 DT 一致的上拉输入，保持输出禁用，再在显示探测前采样；非零初始化的 `.data` 状态随 relocation 保留。late hook 将采样状态和桌面请求传给 Linux，生成器在电量至少 5% 时接受桌面请求。

第一版只读继承配置的提前采样得到 `unavailable`，不算通过。补齐输入配置的新镜像在 RAM 启动中得到 `mocha_power_key_early=released` 和 `mocha_desktop_requested=0`，用户确认充电界面及长按进入桌面正常。该镜像已通过带完整 LNX 备份、预期旧哈希校验及写后回读的安装器持久安装；电脑另存并校验了旧 LNX。新 Android 容器为 571392 字节，entry `0x80a00000`、page 2048，SHA256 `26cf1bef5ebfbf1e0a05f068de1463b8aaed658021ab792ba11c7a99817b0bb4`。六个 U-Boot 存储写入功能仍关闭。

普通冷启动随后通过：用户确认按住电源后接入 USB 可直接进入桌面；实际内核命令行为 `mocha_power_key_early=held mocha_desktop_requested=1`，`mocha-charger.service` 未启动，用户桌面和运行策略服务活动。安装后的完整 LNX 分区 SHA256 为 `0d4d4aff2d4aa94fa3891e1358113f39f74c688dbcdb65dc2a1a57a56e6fa9a0`。该结果覆盖本次插电按住路径，不能解决原厂前级引导器的关机短按门控。

## 备份和 3 GiB APP 计划

扩容前 APP 起点 524288、2612431 个扇区，实际为 1337564672 字节，约 1.25 GiB；UDA 也接近满。APP 后面紧接 AP1、CAC、UDA，不能直接在线扩展根文件系统。

独立 RAM 维护镜像已构建并下载校验，包含 armhf Python、e2fsprogs 和 fdisk 工具；启动脚本保留 eMMC 只读、分区不挂载的保护。镜像 SHA256 `9acc96ed2690b47468e6dd39cda64540aadc5a8a11fa66ced4a6388192317ac5`。e2fsck、sfdisk、resize2fs 已通过 QEMU 基本启动检查，镜像已实机启动，确认 eMMC 和 boot0/boot1 只读、所有分区未挂载。电脑备份程序会检查无挂载、无 holders、磁盘和 boot0/boot1 只读，校验传输两端与电脑回读哈希，再验证 GPT 两份 header 和 entries 的 CRC；合成 GPT 的有效与损坏路径已通过测试。

整盘 15758000128 字节及 boot0/boot1 各 4194304 字节的离线备份已完成，源设备与电脑接收哈希相同，电脑完整回读也一致。发现原有备用 GPT 的 29 项数组只提前 7 个扇区，最后一项被表头覆盖；主表与表头 CRC 正常。严格校验按预期拒绝这种状态。保留原始备份后，仅将设备备用数组前移一个空扇区并修正备用表头位置／CRC；回读确认两份表及 CRC 一致、分区边界未改。详见 [迁移说明](SYSTEM3G.md)。扩容到 3 GiB 需要离线缩小／迁移 UDA、保存 AP1/CAC、保持文件系统 UUID 和分区 GUID，并先更新和验证 initramfs 的精确 APP 大小检查。用户已明确授权清理以前的其他系统。只读与再次挂载审计均未发现当前 Debian 引用旧 L4T；离线 fsck 通过后已删除 L4T_R241，保留其他个人媒体，UDA 空闲 1546560 个 4096 字节块。桥接 initramfs 已写入并核对 SHA256 `453edd88257c3f5822cd3ea337442b76562c7d91021f9b2c6efe325b60fe01e7`，随后已经普通启动验收；所有分区卸载后恢复只读。离线迁移已完成，扩容后的普通启动已通过，完整组件检查仍待完成。

蓝牙仍在 Reset 成功后的 Read Local Version 超时，ALSA 仍无已验收声卡。音频实验模块未装入默认路径；按用户顺序，蓝牙、扬声器、浏览器和硬件视频加速工作放在备份与扩容之后。

## 迁移中的维护环境修正

桥接 initramfs 已经普通启动验收：实际 SHA256 与桥接包一致，`native-runtime`、用户桌面和运行策略活动，用户确认画面与触控正常。重新进入 RAM 后，整盘只读且无分区挂载，重新核对原 GPT、备份、桥接验收与空闲空间。

首次 fsck 因孤立 inode 链提示停止在搬移前。只读完整检查未发现其他问题后，以撤销记录运行完整检查并清除错误标记，保存了原停止记录。随后 resize2fs 又因检查时间早于挂载时间拒绝执行；当时 RAM 时钟为 1970 年，来自维护镜像未做 RTC/UTC 同步。校准内核 UTC 时钟后重新检查；没有强制跳过 resize2fs 的检查，也没有写硬件 RTC。迁移工具新增写前时钟保护、fsck 后时间保护和 APP 预检查。

UDA 成功缩至 2895104 个 4096 字节块，但缩容后的 fsck 再次停止，仍未搬移分区。进一步只读审计发现 86829 个 inode 的删除时间为 epoch 2002–2032 秒，全部位图未分配且链接数为 0；这些是先前在未校准时钟的 RAM 中删除旧 L4T 所产生的时间戳。e2fsck 的低删除时间启发式见 [对应上游代码](https://github.com/tytso/e2fsprogs/blob/v1.47.2/e2fsck/pass1.c#L1393-L1416)，校验完成时间检查见 [resize2fs 上游代码](https://github.com/tytso/e2fsprogs/blob/v1.47.2/resize/main.c#L405-L440)。

仅在完整只读报告没有其他问题、逐项验证上述未分配 inode 后，使用禁用额外 extent 优化、带 e2undo 的完整修复。修复后独立只读 fsck 返回 0，活动 inode 20625 个、空闲块及文件系统 UUID 与修复前相同；撤销文件与日志复制到私人电脑备份并核对哈希。各次停止记录分别保存，仅在确认仍为旧 GPT 且尚未搬移后归档；没有盲目重跑被中断的重叠搬移。之后继续搬移，最终结果另行记录。
